先建立最小因果模型

“代理模式能用、TUN 模式不能用”首先说明远端节点大概率可用。两种模式的差异， 主要发生在入口、权限、路由与 DNS，而不是代理服务器本身。

应用请求 浏览器或命令行发起连接
流量入口 系统代理端口，或 TUN 虚拟网卡
决策层 DNS 解析、路由选择、分流规则
出口 sing-box 节点或本地直连

系统代理为什么容易“看起来正常”

应用主动连接 127.0.0.1:10808，sing-box 可以在代理侧解析域名，不依赖全局路由接管。

TUN 为什么更容易暴露问题

它必须同时满足管理员权限、虚拟网卡、路由、DNS 和分流规则都正确，任何一层失效都会表现为“没网”。

实际排查与修复步骤

顺序遵循“先证明、后修改；先查共同依赖，再查模式差异；每次只改变一个关键变量”。

1

确认核心进程和系统代理是否真的工作

先验证用户所说的“代理模式可以”，避免把节点故障误判成 TUN 故障。

建立基线 
ps aux | rg -i 'v2ray|xray|sing-box'
scutil --proxy
lsof -nP -iTCP -sTCP:LISTEN | rg '10808|sing-box'
curl --proxy http://127.0.0.1:10808 https://www.google.com
得到的证据

sing-box 正在监听 10808；系统 HTTP、HTTPS、SOCKS 代理均指向该端口；代理请求返回 HTTP 200。

为什么进入下一步

节点、协议和代理出口已经被证明可用，因此范围缩小到 TUN 特有的权限、网卡和路由。

2

检查 TUN 网卡和路由有没有真正建立

界面开关不是证据；内核路由表和虚拟网卡才是。

检查数据平面 
ifconfig -a
netstat -rn -f inet
route -n get 1.1.1.1
route -n get 198.18.0.1
得到的证据

最初没有 v2rayN 的 TUN 网卡；IPv4 默认路由仍走 Wi‑Fi en1 → 10.0.0.1。

为什么进入下一步

问题不是“路由规则写错了一点”，而是 v2rayN 根本没有生成并启动 TUN 入站，需要检查实际配置。

专家判断 系统中已有多个 utun，不能看到一个虚拟网卡就认定它属于 v2rayN；必须结合地址、配置和进程归属交叉确认。
3

读取 v2rayN 生成的运行配置，而不是猜设置

运行时配置决定 sing-box 实际做什么。

检查控制平面 
jq '{inbounds,dns,route,experimental}' \
  "$HOME/Library/Application Support/v2rayN/binConfigs/config.json"

jq '.TunModeItem' \
  "$HOME/Library/Application Support/v2rayN/guiConfigs/guiNConfig.json"
得到的证据

EnableTun=false，运行配置只有 mixed 代理入口，没有 "type": "tun"。

为什么进入下一步

TUN 没有进入配置，通常是开关未生效或提权启动失败；下一步应查日志和进程权限。

4

确认提权流程是否失败

macOS 上自动路由 TUN 需要管理员权限，普通用户进程不能完整建立所需网络状态。

定位启动失败 
ps -axo pid,ppid,user,command | rg 'sing-box|v2rayN'
tail -500 \
  "$HOME/Library/Application Support/v2rayN/guiLogs/2026-07-28.txt"

sed -n '1,80p' \
  "$HOME/Library/Application Support/v2rayN/binConfigs/run_as_sudo.sh"
得到的证据

初始 sing-box 以普通用户运行；日志出现 Failed to find a registration for an Interaction，与 sudo 授权交互失败时间吻合。

为什么执行修复

证据链已经闭合：开关触发了提权脚本，但授权交互没有完成。获得用户明确授权后，再从界面重新启用 TUN。

修复动作 A 在 v2rayN 界面重新启用 TUN，让应用重新生成配置并执行自己的 sudo 启动脚本；没有创建永久免密 sudo 规则。
5

证明 TUN 已经真实启动

修复后必须同时验证进程、配置、网卡和路由，不能只看开关变绿。

四重验证 
ps -axo pid,user,command | rg 'sing-box run'
jq '.inbounds' \
  "$HOME/Library/Application Support/v2rayN/binConfigs/config.json"
ifconfig utun60
netstat -rn -f inet
得到的证据

sing-box 已由 root 运行；配置出现 type=tun；utun60 地址为 172.18.0.1；全局分段路由指向该网卡。

为什么仍继续检查

TUN 数据平面已成立，但使用域名访问 Google 仍超时；说明还存在独立的 DNS 问题，而不是继续反复重启 TUN。

6

把“连接失败”拆成 DNS 与 TCP 两个问题

同一网站，用域名失败、固定正确 IP 成功，是非常强的 DNS 证据。

差分实验 
scutil --dns
dscacheutil -q host -a name www.google.com
dig www.google.com A

curl --resolve www.google.com:443:142.250.72.196 \
  https://www.google.com
得到的证据

系统通过路由器 DNS 10.0.0.1 得到错误的 Google 地址；固定正确 IP 后，TUN 下请求返回 HTTP 200。

为什么修改 DNS

传输链路已被证明正常，唯一失败变量是名称解析。修改节点、MTU 或分流规则都不是最小修复。

修复动作 B 将 Wi‑Fi DNS 固定为 8.8.8.8 和 1.1.1.1，并刷新本地 DNS 缓存。 
networksetup -setdnsservers Wi-Fi 8.8.8.8 1.1.1.1
dscacheutil -flushcache
7

端到端验收，而不是“应该好了”

最后验证解析结果、HTTPS、多个站点和 TUN 计数器。

完成验收 
networksetup -getdnsservers Wi-Fi
dscacheutil -q host -a name www.google.com

curl -4 https://www.google.com
curl -4 https://github.com
curl -4 https://1.1.1.1/cdn-cgi/trace

netstat -ibdn | awk '$1=="utun60" {print}'
验收结果

DNS 返回真实 Google 地址；Google、GitHub、Cloudflare 均返回 HTTP 200；utun60 收发计数持续增长。

停止条件

入口、路由、解析、传输和真实业务访问均通过，已达到完整修复标准，无需继续扩大改动。

修复前后对照

检查项 修复前 修复后 意义
TUN 开关 EnableTun=false EnableTun=true 控制面已启用
sing-box 权限 普通用户 root 具备建立 TUN 与路由的权限
TUN 入站 不存在 type=tun 运行配置真实生效
虚拟网卡 无 v2rayN TUN utun60 / 172.18.0.1 数据平面已建立
DNS 10.0.0.1，返回错误地址 8.8.8.8 + 1.1.1.1 消除本地 DNS 污染

作为专家，我是怎么做决策的

专业排障的核心不是记住更多命令，而是让每个命令区分两个以上的竞争假设，并用最小改动验证因果。

01

先缩小故障域

代理模式可用意味着节点与出口可用，所以优先检查 TUN 独有组件，避免无意义地换节点。

02

事实优先于界面

开关显示、托盘图标都可能失真；进程 UID、运行配置、路由表和包计数才是事实。

03

用差分实验隔离变量

域名失败而固定 IP 成功，直接把故障从“整个 TUN”缩小到“DNS 解析”。

04

修最小必要层

DNS 出错就修 DNS，不顺手改 MTU、协议或所有路由；减少副作用和回归面。

05

保留未知，不过度断言

系统里另有 ClashMi 扩展，但没有证据证明它是主因，因此没有直接卸载。

06

以端到端结果停止

只有真实 HTTPS、多个目标与 TUN 流量计数同时通过，才宣布修复完成。

为什么没有直接卸载 ClashMi 网络扩展？
它确实建立了另一套 utun 和补充 DNS，但当时没有证据表明它导致 v2rayN 无法提权，也没有证据表明它阻断全部流量。卸载属于影响更大的操作， 而启用 TUN 并修正 DNS 后已经通过验收，所以遵循最小改动原则保留它。
为什么不设置永久免密 sudo？
永久免密会扩大本机权限暴露面。正确做法是让 v2rayN 使用它自己的提权脚本， 只将需要建立 TUN 的 sing-box 进程提升为 root，而不是让整个应用长期拥有管理员权限。
为什么默认路由仍显示 Wi‑Fi，不代表 TUN 没生效？
sing-box 在 macOS 上可通过若干更具体的分段路由覆盖公网地址空间，同时保留原始 default route 供代理服务器出口使用。路由遵循“最长前缀匹配”，更具体的 TUN 路由会优先于默认路由，因此要结合 route get 和 TUN 计数器判断。

命令索引与用途

目标 命令 回答的问题
进程 ps -axo pid,user,command 谁在运行？是否为 root？
监听端口 lsof -nP -iTCP -sTCP:LISTEN 10808 是否真实监听？
系统代理 scutil --proxy 应用是否被导向本地代理？
网卡 ifconfig -a TUN 是否存在、地址与 MTU 是什么？
路由 netstat -rn / route -n get IP 某个目标最终走哪张网卡？
运行配置 jq '.inbounds,.route,.dns' config.json sing-box 实际收到的配置是什么？
DNS scutil --dns / dig 由谁解析、返回了什么地址？
差分验证 curl --resolve 域名:443:正确IP 失败来自 DNS 还是传输链路？
设置 DNS networksetup -setdnsservers Wi-Fi ... 如何绕开路由器下发的污染 DNS？
最终验收 curl + netstat -ibdn 真实业务访问与 TUN 数据流是否同时正常？
回滚 DNS 如需恢复为 DHCP 自动下发 DNS，可执行： networksetup -setdnsservers Wi-Fi empty
